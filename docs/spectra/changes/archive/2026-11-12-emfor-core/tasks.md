## 2. Checkers

- [x] 2.1 [after: 1.1] Implement the Checker trait with validate and check in crates/emfor-daemon: `CheckResult` with `Up`, `Down(reason)`, `Error(reason)` so Check results are up, down, or error; a `CheckerFactory` registry keyed by the `check` string; and a timeout wrapper that turns an unfinished check into `Down("timeout")`. Verified by unit tests: an unknown kind is rejected by the registry, and a checker that sleeps longer than `timeout` yields `Down("timeout")` under `tokio::time::pause`.
- [x] 2.2 [after: 2.1] Implement the TCP checker: connect returns `Up` and closes, refused returns `Down` with the error text, local socket-creation failure returns `Error`; any `check_options` key is rejected by `validate`. Verified by tests against a local `TcpListener` (listening → up) and a closed port (→ down), and a validation test for `check_options.path`.
- [x] 2.3 [after: 2.1] Implement the HTTP checker using reqwest with rustls (no default features, no redirect following): options `path`, `scheme`, `host_header`, `expect_status` with code and `lo-hi` range entries, `tls_verify`. Verified by tests against a local test server covering every row of the "status matching" example in the health-checking spec, a test that the server sees `Host: api.internal` when `host_header` is set, and a validation test rejecting `["299-200"]`.

## 4. Health state and scheduling

- [x] 4.1 [after: 1.1] Implement the Health state machine with rise and fall as a pure type taking results plus a time source: counters, transitions, and the `error`-only-for-longer-than-`fall × interval` rule that resets to `unknown`. Verified by a table test covering every row of the "state transitions with rise = 2, fall = 3" example and a test for the persistent-errors scenario using an injected clock.
- [x] 4.2 [after: 2.1, 4.1] Implement One task per backend for check scheduling so that Check scheduling with jitter and no overlap holds: first check after a random delay in `[0, interval)`, later waits of `interval` ± `jitter`, checks run sequentially per backend, results fed to the state machine, and Logging of state changes at `info` with service, backend id, old state, new state, and reason. Verified by a unit test of the wait calculation with a seeded RNG (bounds 1.8s–2.2s for 2s/10%, exactly 1s for 0%), a `tokio::time::pause` test showing no overlapping checks when a check takes longer than `interval`, and a `tracing-test` assertion on the transition log line.

## 5. State store

- [x] 5.1 [after: 1.2] Implement the LMDB file layout and Single writer per store via the Writer lock against a second daemon: take an exclusive `flock` on `<path>.writer` (on failure, an error naming that file and exit status 1), then open with heed using `MDB_NOSUBDIR`, the default database only, `map_size`, and apply `file_mode` / `lock_file_mode`. Verified by tests that the data and `-lock` files exist with the configured modes, and that a second open of the same path fails with the lock file named in the error.
- [x] 5.2 [after: 4.1, 5.1] Implement the Single writer task for the LMDB store: a channel-fed task that commits immediately on any health state change, commits the heartbeat plus changed `checked_at` / `reason` once per second, computes all_down reflects absence of healthy backends, and handles Write failures are surfaced, not fatal by logging at `error` and retrying at the next tick. Verified by tests that read the store with heed: heartbeat increases across 2s (Heartbeat and timely state updates), a state change is readable before the next heartbeat tick, every row of the "all_down computation" example, and an injected commit failure that logs an error and succeeds on the next tick.
- [x] 5.3 [after: 3.2, 5.2] Implement the Store lifecycle on start, reload, and shutdown: Fresh state on every start (write meta keys, delete all `svc/*`, write every service with all backends `unknown`) and Store updates on reload (delete removed services, add new services and backends as `unknown`, reset a service whose `check` or `check_options` changed, keep state when only timing or `on_all_down` changed). Verified by tests for the old-state-discarded scenario and each of the three reload scenarios in the state-store spec.

## 6. Daemon wiring and acceptance

- [x] 6.1 [after: 3.3, 2.2, 2.3, 4.2, 5.3] Wire the daemon's Reload and shutdown via unix signals: Reload on SIGHUP applies only a fully valid config (valid config is applied; any validation error, including a changed `[store]` table, is logged and the previous config keeps running), and Clean shutdown marks the store stale (`SIGTERM` / `SIGINT` stop checks, write `meta/heartbeat = "0"`, exit 0). Verified by integration tests that spawn the `emfor` binary with a temp store: adding a service plus `SIGHUP` makes its record appear; an invalid edit plus `SIGHUP` leaves the store unchanged; changing `[store] path` plus `SIGHUP` logs "store settings require restart"; `SIGTERM` exits 0 with `meta/heartbeat` reading `0`; a second daemon on the same store exits 1.
- [x] 6.2 [after: 6.1] Add examples/emfor.toml covering a `tcp` and an `http` service, with a comment explaining that readers need write access to the `-lock` file and how to tighten `lock_file_mode` to a group, plus an end-to-end acceptance test: a backend that stops accepting connections becomes `unhealthy` in the store after `fall` checks and returns to `healthy` after `rise` checks once it listens again. Verified by `emfor --check-config --config examples/emfor.toml` exiting 0 and by the acceptance test passing under `cargo test --workspace`.
