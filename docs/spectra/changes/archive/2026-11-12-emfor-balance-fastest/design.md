## Context

emfor 在每台應用主機上跑一個 daemon。每個後端有一個 tokio task（`crates/emfor-daemon/src/schedule.rs` 的 `spawn_backend`），負責執行檢查、更新 `BackendHealth`，再把 `BackendUpdate` 送給 store writer（`crates/emfor-daemon/src/writer.rs`）。writer 保管所有服務記錄，把它同步到 DNS server 使用的記憶體狀態，並寫入 LMDB 給 client 讀。目前的分配方式有 round-robin、sticky、failover、weighted、locality；不認得的 `balance` 字串會讓 client 和 DNS 改用 round-robin。

emfor-balance-2 延後 `fastest` 有兩個原因：單次檢查的耗時起伏很大；而且如果同一台主機上的每個 client 都送往延遲最低的那台後端，那台就要承擔整台主機的流量。

每個 daemon 都從自己的主機量測，記下的延遲正是這台主機上應用程式會遇到的延遲，所以以主機為單位的「最快」不需要主機之間協調。

Task 1.1（記錄延遲）已完成。第一輪實驗（見「實驗結果」）顯示：如果每次查詢都從延遲重新算出快組，只要有後端落在門檻邊緣，成員每幾秒就會變一次；只有在兩次判斷之間記住成員（遲滯），快組才會穩定。client 每次查詢都從頭讀 store，什麼都記不住，所以判斷必須移到 daemon。再者，讀取端完全不該需要懂 `fastest`：最差的讀取端是透過 DNS 查詢的程式，它只能收到答案。因此 daemon 算出快組，並把它發布成可挑選的集合（`pool`）；client 只在這個集合裡輪流，和 round-robin 的輪流方式相同。這符合 emfor 的分工：daemon 判斷後端，client 只問答案。

## Goals / Non-Goals

**Goals:**

- 為每個後端記錄平滑後的檢查延遲，保存在記憶體和 store 中。
- 由 daemon 單獨決定快組，並發布為服務的 `pool`；client 在 `pool` 裡輪流，不含任何延遲或成員判斷邏輯；DNS server 依同一個判斷回答。
- 讓流量分散到速度差不多的後端，而不是全部送往同一台。
- 後端延遲在門檻邊緣起伏時，快組仍保持穩定。
- 用實測確認常數，包含一台明顯較慢的後端；沒通過門檻就停止這個 change。

**Non-Goals:**

- 量測應用程式請求的延遲或負載；只使用健康檢查的耗時。
- 依延遲加權（機率與速度成正比）。不採用：較難說明與測試；快組加上 round-robin 已經能分散流量。
- 讓門檻、遲滯或平滑權重可以設定。
- 與健康檢查分開的專用延遲探測。
- 主機之間協調，或在 daemon 之間共享延遲。
- 把每次查詢的挑選移到 daemon：client 直接讀 LMDB，並保有自己的 round-robin 計數器，和其他分配方式一樣。

## Decisions

### 延遲是 up 檢查的耗時

daemon 用單調時鐘量測 `run_check` 從開始前到回傳的時間，只有結果是 `up` 時才使用這個耗時。`down` 和 `error` 不改變延遲。同一個服務的所有後端使用同一種檢查，所以固定開銷（`exec` 的程序啟動、外掛的一來一回）對所有後端都一樣，比較仍然公平。只發生一次的準備工作不算在內：計時開始前，daemon 先呼叫檢查器的 `prepare`，`http` 檢查器在這裡建立該後端的 HTTP client（含 TLS 設定）。否則第一個樣本會多出這段時間，又因為第一個樣本直接成為延遲、新樣本權重只有 0.05，偏高的值要約 2 分鐘才會消退，啟動時可能讓不該進快組的後端進入，之後留在離開門檻內。

考慮過的替代方案：只量 TCP 連線時間。不採用，因為每個檢查器都需要第二套程式路徑，而且外掛沒有這種時間。

### 以 EWMA 平滑，新樣本權重 0.3

在本 change 中**被取代**，由「以 EWMA 平滑，新樣本權重 0.1」取代。Task 1.1 實作了權重 0.3；task 1.2 修改它。

### 以 EWMA 平滑，新樣本權重 0.1

**Supersedes**: emfor-balance-fastest / 以 EWMA 平滑，新樣本權重 0.3

在本 change 中**被取代**，由「以 EWMA 平滑，新樣本權重 0.05」取代。Task 1.2 實作了權重 0.1；task 1.3 修改它。

`latency = round(0.1 × sample + 0.9 × previous)`，單位為整數微秒，以 `(sample + 9 × previous + 5) / 10` 計算；延遲為空之後的第一個樣本直接成為延遲。第一輪實驗中，權重 0.3 加上遲滯，http 服務每小時仍有 80 次快組變動，權重 0.1 則是 6.7 次（實測，見「實驗結果」）。以預設間隔 2 秒檢查時，一次持續的階梯變化在 10 次檢查（20 秒）後約反映 65%；這種較慢的反應可以接受，因為 `fastest` 處理的是穩定的差異，而不健康的後端是透過健康檢查、不是透過延遲離開候選名單。

### 以 EWMA 平滑，新樣本權重 0.05

**Supersedes**: emfor-balance-fastest / 以 EWMA 平滑，新樣本權重 0.1

`latency = round(0.05 × sample + 0.95 × previous)`，單位為整數微秒，以 `(sample + 19 × previous + 10) / 20` 計算；延遲為空之後的第一個樣本直接成為延遲。使用者在第二輪實驗後於 2026-11-12 選定：權重 0.1 在 `interval = "1s"` 時未通過門檻第 (2) 項（每小時 7.7 與 6.8 次變動），只在預設 2 秒時通過；權重 0.05 兩種間隔都通過（每小時最多 4.8 次，實測，見「第二輪」）。權重是以每次檢查計算，間隔越短、每小時樣本越多；0.05 讓間隔短到 1 秒時仍有餘裕。以預設間隔 2 秒檢查時，一次持續的階梯變化在 20 次檢查（40 秒）後約反映 64%；理由同前，可以接受：`fastest` 處理的是穩定的差異，不健康的後端是透過健康檢查、不是透過延遲離開候選名單。

### 後端變成不健康時清空延遲

後端狀態變成 `unhealthy` 時，它的延遲變成空值，恢復後重新開始累計，不沿用故障前量到的值。延遲和 `BackendHealth` 存放在同一個後端 task 狀態裡，所以遵守既有規則：daemon 啟動時為空；重新載入時後端狀態保留就保留；後端被重設為 `unknown` 時清空。

### store 欄位 latency_us，格式版本維持 1

每個後端物件多一個 `latency_us`：非負整數，空值時為 `null`。讀取端本來就忽略不認得的欄位，遇到不認得的 `balance` 也會改用 round-robin，所以舊 client 對新 daemon 照常運作，`meta/schema_version` 維持 `1`。沒有 `latency_us` 時視為 `null`。只有延遲變動時，最晚在下一次心跳寫入，和 `checked_at` 相同。client 不使用 `latency_us`；它是給維運人員和除錯用的。

### 快組：與最快者相差 1.5 倍或 1 ms 以內

在本 change 中**被取代**，由「daemon 以遲滯決定快組成員」取代。

### 在快組內以 round-robin 挑選

在本 change 中**被取代**，由「client 與 DNS 在快後端之間以 round-robin 挑選」取代。

### daemon 以遲滯決定快組成員

**Supersedes**: emfor-balance-fastest / 快組：與最快者相差 1.5 倍或 1 ms 以內

對每個 `fastest` 服務，writer 在記憶體中為每個後端保存一個「快」旗標；任何後端的狀態或延遲改變時、以及重新載入後，重新計算整個服務。範圍是該服務兩種 IP 版本中 `healthy` 且有延遲的後端；其他後端都不算快。令 `min` 為範圍內的最低延遲（微秒）：

- 不快的後端在 `latency ≤ max(min × 3 / 2, min + 1000)` 時變快（進入門檻）；
- 快的後端在 `latency ≤ max(min × 2, min + 2000)` 時維持快（離開門檻），超過就不快。

使用整數運算，`min × 3 / 2` 無條件捨去。延遲等於 `min` 的後端一定是快的，所以快組為空，正好就是沒有任何健康且有延遲的後端。變成不健康、被重設、或新加入的後端，一開始都不快。

離開門檻比進入門檻寬，邊緣的後端就不會每次檢查都翻轉。第一輪實驗中，這讓 http 的快組變動從每小時 1,647 次降到權重 0.3 時的 80 次、權重 0.1 時的 6.7 次（實測）。進入門檻的常數（1.5 倍、1 ms）沿用最初的規劃；離開門檻（2 倍、2 ms）是新加的，並由第二輪實驗（task 2.1）連同權重 0.05 一起確認。

只有 `fastest` 服務會計算成員；其他服務用不到。考慮過的替代方案：由 client 從 `latency_us` 算出快組（最初的規劃）。不採用：client 無法保存遲滯狀態，而且每種 client 語言都得實作延遲規則。用單一固定門檻加更強的平滑：不採用，因為任何單一門檻都會讓剛好落在線上的後端翻來翻去。

### client 與 DNS 在快後端之間以 round-robin 挑選

在本 change 中**被取代**，由「daemon 發布 pool，讀取端在其中輪流」取代。

### store 欄位 fast

在本 change 中**被取代**，由「store 欄位 pool」取代。每個後端一個旗標，仍然要求每個讀取端自己過濾後端；讀取端應該只收到集合。

### daemon 發布 pool，讀取端在其中輪流

**Supersedes**: emfor-balance-fastest / client 與 DNS 在快後端之間以 round-robin 挑選

對 `fastest` 服務，daemon 的答案就是 pool：快後端的 id，依設定檔順序。client 看到 store 未過期、且 `pool` 不是空的，就用自己程序內的 round-robin 計數器在 `pool` 列出的後端之間輪流；否則（心跳過期、`pool` 為空或不存在）完全照 `round-robin` 挑選，包含全部不健康時的規則。client 不讀 `latency_us`，也不自己判斷成員，並忽略 affinity key。DNS server 從記憶體狀態使用同一份 pool：A/AAAA 用該服務各 IP 版本的計數器，在 pool 中該版本的後端之間輪流；pool 中沒有該版本的後端時，照 `round-robin` 在該版本的全部候選間挑選。因此 pool 全是 IPv6 的服務，A 查詢會以 round-robin 回答；預期在意這點的混合版本服務很少。

### store 欄位 pool

**Supersedes**: emfor-balance-fastest / store 欄位 fast

`fastest` 服務的記錄多一個 `pool`：後端 `id` 字串的陣列，依設定檔順序；沒有快後端時為空陣列。其他服務的記錄沒有 `pool`。pool 成員一定健康，因為成員資格要求 `healthy`，所以服務全部不健康時 pool 一定是空的。舊 client 忽略 `pool`。只有 pool 變動時，最晚在下一次心跳寫入；健康狀態改變時立即寫入，連同為它重新計算的 pool。

### SRV：快組 priority 0，其他 priority 1

對 `fastest`，pool 中候選的 SRV 記錄給 priority 0，其他候選給 priority 1，weight 1，順序是輪換後的候選清單依 priority 穩定排序，和 `locality` 相同。pool 為空時，所有候選都給 priority 0。SRV 候選包含兩種 IP 版本，正好符合 pool 以整個服務為範圍。

### 先實驗再實作選擇

Task 2.1 用資料決定常數。原始樣本來自每次 up 檢查的 `debug` 記錄；任何一組常數下的快組行為，都可以用和結果一起保留的腳本，從這些樣本離線模擬。門檻：在選定的常數下，(1) 中位延遲在最快後端中位數的進入門檻以外的後端，在快組裡的時間少於整段實驗的 1%；(2) 每個服務的快組成員每小時最多變動 6 次。兩個門檻都是判斷值；每輪實驗記錄實際數值。如果權重（0.05–0.3）、進入門檻（1.25–2 倍、0.5–2 ms）和離開門檻（1.5–3 倍、1–5 ms）沒有任何組合通過門檻，change 就停在 task 2.1 並記錄結果，`fastest` 在 docs/spectra/config.yaml 維持延後。

- 離開門檻等於進入門檻（無遲滯）時，每一列都未通過第 (2) 項（每小時 8.7 到 1,350 次變動）。
- 每小時變動次數來自很小的計數（7.7 次/小時就是 62 分鐘內 8 次），所以原定與替代組合只差幾次事件。

結論：原定常數（權重 0.1、進入 1.5 倍 / 1 ms、離開 2 倍 / 2 ms）在預設 2 秒間隔下通過門檻，但在 1 秒時以些微差距未通過第 (2) 項，因為權重以每個樣本計算，間隔越短每小時樣本越多。相同門檻下權重 0.05 兩種間隔都通過；權重 0.1 加離開門檻 3 倍 / 3 ms 也通過，但會讓慢到 3 倍的後端留在 pool。選定（使用者決定，2026-11-12）：權重 0.05、進入門檻 1.5 倍 / 1 ms、離開門檻 2 倍 / 2 ms，記錄於「以 EWMA 平滑，新樣本權重 0.05」。門檻結果：通過。

## Implementation Contract

**Behavior.**
- `balance = "fastest"` 在服務表格和 `[defaults]` 中都有效；不認得的值所產生的設定錯誤會列出 `fastest`。
- 所有服務的 store 後端物件都帶 `latency_us`（整數微秒或 `null`）；`fastest` 服務的記錄帶 `pool`。
- 對 `fastest` 服務，A/AAAA 回答和 client 查詢在 pool 裡輪流；pool 為空（或 A/AAAA 時 pool 沒有該 IP 版本的後端）時等同 `round-robin`。SRV 回答給 pool 成員 priority 0。
- 每次 up 檢查有一行 `debug` 記錄，包含服務、後端和以微秒計的原始耗時（task 1.1 已完成）。

**Interface / data shape.**
- Store：後端物件多 `"latency_us": 1834`；`fastest` 服務記錄多 `"pool": ["10.0.0.11:8080", "10.0.0.12:8080"]`，寫在 `backends` 之後。
- Rust：`emfor_format::ServiceRecord` 多 `pool: Option<Vec<String>>`（`None` 時不輸出）；`Balance` 多 `Fastest`；成員規則是 daemon（writer 端）的一個函式，以規格範例表做單元測試。client 只讀 `pool`。
- 一致性測試：`tests/conformance/v1/cases.json` 新增 `fastest` 案例（非空 pool、空 pool、沒有 pool、心跳過期但有 pool、pool 列出不存在的後端 id）。

**Failure modes.**
- pool 為空（剛啟動、所有健康後端都還沒有延遲、或全部不健康）：照一般的全部不健康規則，在所有候選間 round-robin，不另外通知。
- pool 中的 id 對不上任何後端（daemon 正確時不會發生）：client 略過它；沒有剩下的就用 round-robin。
- 舊 client 對新 daemon：round-robin，忽略 `latency_us` 和 `pool`。
- 新 client 對舊 daemon：那個 store 裡不會出現 `fastest`。

**Acceptance.**
- 單元測試：權重 0.05 的平滑表；快組成員範例表（進入、維持、離開、不健康、沒有延遲）；daemon 與 client 在 pool 中的挑選；`fastest` 的 SRV priority。
- 整合測試：一個 daemon 測試，回應會延遲的測試後端在兩台都健康且有延遲後，不會出現在 A 回答中（因 macOS 限制改由其他測試涵蓋，見 tasks.md 的 Change notes）；一個 store 測試，`fastest` 服務的 `pool` 列出唯一健康的後端，該後端變成不健康後為空。
- 一致性測試案例在 Rust client 中通過，並透過 `emfor-conformance` driver 在每個包裝層通過。
- 本機檢查：macOS 與 Debian image 的 fmt、clippy、test；`tests/resolver/run.sh` dnsmasq 與 unbound。

**Scope.** 範圍內：以上全部。範圍外：可設定的常數、依延遲加權的挑選、獨立的探測、由 daemon 做每次查詢的挑選、FreeBSD 驗證（本機仍無法進行）。

## Risks / Trade-offs

- [檢查延遲不等於請求延遲] → 已寫進文件：`fastest` 偏好的是從這台主機看健康檢查回應最快的後端；請選擇接近實際流量的檢查。
- [權重 0.05 反應較慢] → 接受：持續的變化要幾十秒才會移動一台後端；故障由健康檢查處理。
- [某台快很多時，快組可能只有一台] → 刻意如此；如果不能讓單一後端承擔全部流量，請用 `weighted` 或 `locality`。
- [A/AAAA 混合 IP 版本] → 以整個服務為範圍的 pool 可能讓某個 IP 版本沒有成員；該版本改用 round-robin。
- [第一輪用的是同一台機器上的 VM] → 第二輪加入了明顯較慢的後端；真實網路的抖動仍無法在本機量測，已記在結果中。
- [store 寫入增加] → 只有 `latency_us` 和 `pool` 變動時，併入心跳一起寫（每秒最多一次），和現在的 `checked_at` 相同。
